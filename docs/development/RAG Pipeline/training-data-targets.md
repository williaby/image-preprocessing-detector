## Project B – OCR Orchestration, Layout & Reading Order

**Scope:** Layout detection, table structure detection, reading order, parasitic content, handwriting vs print regions, language flags. OCR engines are mostly external but need **evaluation sets**.

```markdown
## Project B – Data Readiness Matrix

| Task / Capability                           | Target Train Set (Scale)                                           | Target Validation Set                           | Coverage Dimensions (Must Include)                                                                                         | Readiness Criteria (You’re Done When…)                                                                                     | Current Status (Fill In) |
|--------------------------------------------|--------------------------------------------------------------------|-------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|--------------------------|
| B1 – Layout detection (DocLayNet-like)     | 10k–20k pages with bounding boxes + class labels (Text, Title, Section-Header, Table, Picture, Caption, Footnote, Header, Footer, List-Item, Formula) | 2k–3k pages                                      | Single column, two-column, multi-column, slides, forms, reports, historical docs; mix of clean & degraded pages           | mAP@0.5 ≥ 0.82 and mAP@0.5–0.95 ≥ 0.70 across classes; no critical class with AP < 0.70                                     |                          |
| B2 – Parasitic content detection           | Subset of B1 with explicit header/footer/page-number/watermark tags (~5k pages)                          | 1k–2k pages                                      | Repeated headers/footers across pages, page numbers in various positions, watermarked PDFs with different opacity/orient.  | Header/footer recall ≥ 0.9, precision ≥ 0.85; page numbers reliably isolated; watermarks detected on most visible cases     |                          |
| B3 – Table region detection                | 5k–10k pages with table bounding boxes                             | 1k–2k pages                                      | Simple tables, borderless tables, multi-page tables, dense financial tables, academic tables                              | Table AP ≥ 0.85; low false positives on non-table regions in reports and papers                                            |                          |
| B4 – Table structure recognition           | 10k–50k **tables** with cell/row/column structure annotations      | 1k–3k tables                                     | Simple grids, merged headers, multi-level headers, sparsely populated tables, borderless and dense tables                 | GriTS F1 > 0.85 and/or TEDS > 0.9 on validation; complex merged-header tables not consistently broken                       |                          |
| B5 – Reading order prediction              | 2k–5k pages with full reading order annotations                    | 500–1k pages                                     | Single column, dual column, multi-column, docs with sidebars, embedded figures/tables, footnotes and endnotes             | Pairwise RO F1 ≥ 0.85; Kendall’s Tau ≥ 0.8 on validation; dramatic RO failures rare in multi-column academic papers        |                          |
| B6 – Caption–figure & footnote linking     | 3k–6k pages with figure–caption links and footnote–marker links    | 500–1k pages                                     | Technical/academic papers, reports with figures and tables, legal docs with footnotes                                     | ≥ 90% correct linking for captions; ≥ 90% correct footnote linking in validation set                                       |                          |
| B7 – Handwriting region detection          | 5k–10k text regions labeled as printed vs handwritten (from layout text blocks)                         | 1k–2k regions                                    | Forms, annotated documents, educational material, mixed-mode pages with both print and handwriting                         | F1 ≥ 0.9 for handwriting vs printed; performance similar across document domains                                            |                          |
| B8 – Language / script detection           | 5k–10k documents/pages with primary language + “has_non_latin” flags                                   | 1k–2k docs/pages                                 | English + Western European; at least some Cyrillic, CJK, right-to-left; both clean and noisy scans                         | High precision in detecting non-Latin; misclassification rate low enough not to break routing decisions                     |                          |
| B9 – OCR engine comparison sets            | 2k–5k pages with **trusted ground truth** (or near-ground-truth) text for engine comparison             | 500–1k pages                                     | Same pages run through your primary OCR, secondary OCR, and baseline OCR; covering major domains and quality levels        | Clear performance ranking between engines; no domain where primary engine is catastrophically worse than a fallback         |                          |
| B10 – Complex layouts (stress set)         | 500–1k “nightmare pages” specifically curated for stress-testing layout+RO                              | 200–300 pages                                    | Multi-column + nested tables + sidebars + equations + images; historical messy scans                                     | These pages are mostly “handled” (no total meltdown); qualitative review shows stable behavior                             |                          |
```

## Project D – Embedding & Vector Store Integration (RAG)

**Scope:** Use normalized chunks & trust metrics from C to create embeddings, index into vector DB, and validate retrieval performance.

```markdown
## Project D – Data Readiness Matrix

| Task / Capability                           | Target Train / Eval Set (Scale)                                       | Coverage Dimensions (Must Include)                                                                                     | Readiness Criteria (You’re Done When…)                                                                                     | Current Status (Fill In) |
|--------------------------------------------|------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|--------------------------|
| D1 – RAG benchmark corpora                 | 200–500 documents per **target domain** (e.g., legal, financial, technical, internal docs)                | Mix of lengths (short memos → long reports); various layouts; includes messy real-world docs, not just pristine PDFs   | For each domain, you can run retrieval evals with non-trivial size; no domain has “only 3 test docs”                       |                          |
| D2 – Q&A / label sets for retrieval        | 20–100 Q&A pairs per domain, grounded in specific documents/slices                                       | Different difficulty levels; questions requiring tables, figures, and multi-span reasoning                              | Retrieval metrics (e.g., NDCG, recall@k) are stable and sensitive to configuration changes                                  |                          |
| D3 – Embedding model comparison sets       | Same corpora as D1+Q&A labels                                         | Enough variety to distinguish strengths/weaknesses between embedding models (general vs domain-specific, multilingual…) | Swapping embedding models shows clear, measurable differences; best model is chosen on evidence, not vibes                  |                          |
| D4 – Trust-aware retrieval evaluation      | RAG corpora where chunks have trust scores from C                     | Mixed trust levels; some low-trust but semantically important content; some high-trust trivial chunks                  | Using trust scores in ranking / filtering improves effective retrieval metrics vs ignoring them                             |                          |
| D5 – Multi-collection / namespace behavior | Multiple small corpora representing different projects or tenants     | Documents with overlapping topics across namespaces, and disjoint ones                                                 | Namespacing & routing errors are rare; retrieval stays inside the right collection unless explicitly configured otherwise   |                          |
| D6 – Latency / scalability test set        | Synthetic or real load: thousands of chunks per index; hundreds of queries | Representative size of real deployment: large-enough vector space to matter                                           | Index build times, query latency, and memory usage are within acceptable bounds; performance stays stable under load        |                          |
| D7 – Security / PII checks                 | Sample corpora with known sensitive content (for internal-only testing)                                    | PII, secrets, or confidential markers; multiple doc types                                                              | Indexing pipeline can be configured to exclude or redact sensitive chunks; tests confirm nothing leaks in unintended indices |                          |
```
