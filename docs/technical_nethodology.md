1. Introduction: A Modular "Detect, Correct, and Route" FrameworkThis document outlines the technical methodology for building the document triage tool specified in the "Project Mandate." The "how" is a modular, multi-stage pipeline. The core strategy is "Detect, Correct, and Route":Detect a document's file-level (e.g., PDF type) and image-level (e.g., skew, resolution) characteristics.Correct foundational image flaws that are best handled by OpenCV in a single pass (e.g., de-skew, upsample, binarize).Route the corrected image and its metadata to the specialized downstream processing engine best equipped to handle its content (e.g., layout-aware OCR, vision model, or HTR engine).This process is broken down into four primary phases.2. Phase 1: Detecting and Correcting Image QualityThis phase uses efficient OpenCV functions to quantify and fix physical image defects. This is the primary pre-processing step for all image-based documents.How to Detect Blurriness:Technique: Variance of the Laplacian.[14]Logic: The cv2.Laplacian operator is a high-pass filter. A sharp, in-focus image has strong edges, producing a high variance. A blurry image has smeared edges, producing a low variance.[14]Action: Detect only. The "blur_score" is calculated and reported in the JSON. We do not attempt de-blurring, as it is complex and can introduce artifacts.How to Detect and Correct Document Skew:Technique: cv2.minAreaRect and cv2.warpAffine.[15]Logic:Detect Angle: The image is thresholded, and the coordinates of all content pixels are fed into cv2.minAreaRect. This function finds the smallest bounding rectangle for the content and returns its precise angle.[15]Correct Skew: This angle is then used to create a rotation matrix (cv2.getRotationMatrix2D) and the image is automatically de-skewed using cv2.warpAffine.[15]Action: The original skew angle is reported in the JSON, and the corrected, de-skewed image is passed to all subsequent phases.How to Correct Low Resolution (Upsampling):Technique: cv2.resize with high-quality interpolation.Logic:Get DPI: The tool will attempt to read the image's DPI from its metadata (e.g., PyMuPDF's Page.get_images() for PDFs or PIL/EXIF tags for JPEGs).Check DPI: If the DPI is < 300 or unavailable, the tool assumes a low resolution.Upsample: The image is upsampled using cv2.resize to achieve an effective 300 DPI, which is ideal for OCR. The interpolation method must be high-quality, such as cv2.INTER_CUBIC or cv2.INTER_LANCZOS4.Action: The original DPI is reported in the JSON, and the upsampled image is used for all subsequent analysis.How to Correct Non-Uniform Illumination (Binarization):Technique: cv2.adaptiveThreshold.Logic: Many scanned documents suffer from uneven lighting (e.g., shadows, faded text). A simple "global" threshold (like Otsu's) will fail, either washing out faded text or retaining dark shadows. Adaptive thresholding calculates a different threshold for different regions of the image, producing a much cleaner black-and-white result.Action: This clean, binarized image is the primary input for the Layout Analysis (Phase 2) and Specialized Content (Phase 4) detectors.How to Detect Noise (Stains, Fading):Technique: Histogram Analysis and Connected Component Analysis.Logic: A faded document's grayscale histogram will be a single, compressed peak.[16] Stains or "pepper" noise can be identified using cv2.connectedComponentsWithStats by finding a high count of tiny "blobs" or a few very large, non-text-like "blobs".[17]Action: Detect only. A "noise_score" is reported in the JSON.3. Phase 2: Deconstructing Layout and StructureThis phase uses the corrected, binarized image from Phase 1 and feeds it into a deep learning model to understand the document's spatial semantics.How to Detect All Layout Elements (The Core Engine):Technique: A deep learning object detection model (e.g., YOLO, RT-DETR) trained on the DocLayNet dataset.[5, 18, 19]Logic: The DocLayNet dataset is the "gold standard," providing annotations for 11 critical layout classes: Text, Title, List-Item, Table, Picture, Caption, Formula, Page-Header, Page-Footer, and Footnote.[20, 5]Output: A JSON list of bounding boxes for every layout element on the corrected page.How to Handle Multi-Column Text and Parasitic Content:Logic: With the detector's output, this becomes a simple programmatic sort.Parasitic Content: We flag all bounding boxes labeled Page-Header or Page-Footer.[20] The downstream process will use this to discard text from these regions, cleaning the context.[7]Multi-Column: We check for multiple Text blocks [20] that overlap vertically but not horizontally. This flags the document as "Multi-Column," instructing the downstream parser to extract text sequentially (all of "column 1" then all of "column 2") to ensure correct reading order.How to Handle Tables (A Two-Step Process):Step 1 (Table Detection): The DocLayNet model provides the bounding box for the Table.[21, 20]Step 2 (Table Structure Recognition): The image chip for just the table is routed to a specialized model. A semantic segmentation model (like in DeepDeSRT [22]) is a robust method. This model is trained to find rows and columns as distinct pixel-level segments.[22]Action: The JSON will contain the bounding box for the table and, if structure recognition is run, the coordinates of its cells. This enables the downstream RAG pipeline to treat the table as structured data (e.g., CSV or JSON) rather than "word soup".[23]4. Phase 3: Differentiating File Format PathologiesThis phase uses file-level metadata and a hybrid visual-reconciliation approach to handle non-visual challenges.How to Handle Office Formats (.docx, .xlsx):Technique: File-type routing.Logic: These files are not sent to the CV pipeline. They are flagged and routed to specialized libraries (e.g., python-docx) and parsers (like LlamaParse) that can handle their XML-based structures, including tracked changes, embedded objects, and merged cells.[24, 11]How to Differentiate PDF Types:Technique: Programmatic text extraction attempt.Logic: We use a library (e.g., PyMuPDF) to try to extract digital text."Image-Only" PDF: If the extractor returns zero text objects, it is a scanned image.[9] It is rendered as an image and sent to the full CV pipeline (Phase 1 and 2)."Born-Digital" PDF: If the extractor does return text objects, it is a born-digital file.[9] This triggers "visual reconciliation."How to Solve the "Born-Digital" (x,y) Scramble:The Problem: Born-digital text is 100% accurate, but its extraction order is based on (x,y) coordinates, not reading order, which scrambles multi-column layouts.[8, 10]Technique: Visual Reconciliation.[25]Logic:Extract Digital Text: Get all text strings with their (x,y) coordinates.Extract Visual Layout: Render the page to an image and run our DocLayNet model (from Phase 2).Reconcile: We perform a "geometric sort".[25] We iterate through the visual layout blocks (e.g., Text box 1, then Text box 2) in their correct reading order. For each block, we gather only the digital text strings whose (x,y) coordinates fall inside its bounding box. This uses the visual structure to restore the correct semantic order to the digital text.5. Phase 4: Handling Specialized Content ("Detect and Route")This phase uses the corrected, binarized image from Phase 1 to find content that will fail standard OCR and routes it to a specialist model.How to Handle Handwritten Text:Technique: Zone Classification and Routing.Logic (Detect): First, detect all Text blocks (from Phase 2). Then, run a classifier on each block's image chip to label it as "Printed" or "Handwritten." This can be a simple CNN [26] or a model trained on texture features (like Bag-of-Visual-Words [27, 28]).Logic (Route): All image chips flagged as "Handwritten" are sent to a dedicated Handwritten Text Recognition (HTR) engine (e.g., Google Vision API [29, 30] or Transkribus [31]). Standard OCR will fail on this content.[32]How to Handle Mathematical Equations:Technique: Object Detection and Routing.Logic (Detect): The DocLayNet-trained model from Phase 2 already has a Formula class.[20] This model finds the bounding box for all mathematical notations.Logic (Route): The image chip inside this Formula box is extracted and sent to a specialized "Math OCR" model, such as Nougat [1, 33, 34] or pix2tex [33], which are designed to parse 2D structures and output machine-readable LaTeX. Standard OCR fails because it reads line-by-line, destroying 2D syntax.[1, 13]
