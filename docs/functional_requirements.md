1.0 Introduction1.1 PurposeThis document specifies the detailed functional and non-functional requirements for the "RAG Triage Tool." This tool is a pre-processing validation and correction system designed to analyze and classify all incoming documents. Its purpose is to detect a range of quality, format, and content issues; perform foundational image corrections; and output a structured JSON metadata file. This JSON file will be used to route each document to the correct, specialized processing workflow.1.2 ScopeIn-Scope: This system is responsible for (1) accepting a single document file, (2) analyzing the file to identify properties, (3) running a series of CV-based and file-based detectors, (4) performing foundational image corrections that are most effectively handled by OpenCV (e.g., de-skewing, upsampling), and (5) outputting a single JSON file detailing the original issues and the corrections applied.Out-of-Scope: This system will not perform full-page OCR or text extraction (other than what is necessary for classification). It is not responsible for downstream parsing logic (e.g., table-to-JSON), semantic chunking, or vectorization. It will only perform corrections explicitly defined in the functional requirements.1.3 AudienceThis document is intended for the development team, QA/Test engineers, and project management.2.0 Functional Requirements (FR)FR-1: General System & File HandlingFR-1.1: The system shall accept a single file input via a file path or byte stream.FR-1.2: The system shall support the following file extensions:Images: .jpg, .jpeg, .png, .tiff, .bmpPDFs: .pdfOffice: .doc, .docx, .xls, .xlsxFR-1.3: The system shall output a single, structured JSON metadata file that conforms to the "Triage JSON Schema Definition."FR-1.4: The system shall gracefully handle and log errors for:Unsupported file formats.Corrupted files that cannot be opened.Password-protected or encrypted files.FR-2: File Format AnalysisFR-2.1: The system shall analyze all .pdf files and classify the file type as one of:"Image-Only": Contains no extractable digital text (i.e., a scanned document).1"Born-Digital": Contains extractable digital text and no significant image-based content.2"Hybrid": Contains both extractable digital text and significant embedded images that also contain text.3FR-2.2: The system shall identify .pdf Portfolio files and flag them as "Portfolio" (processing of sub-files is out-of-scope for this tool).FR-2.3: The system shall identify .doc/.docx files and flag their document_type as "Office-Word".FR-2.4: The system shall identify .xls/.xlsx files and flag their document_type as "Office-Excel".FR-3: Image Quality Detection & Correction (Per-page)For all image files and for each page of an "Image-Only" or "Hybrid" PDF:FR-3.1: The system shall calculate a quantitative "blur_score" based on the variance of the Laplacian.4 The JSON output shall report this score.FR-3.2: The system shall detect the document's "skew_angle" in degrees, using a robust method such as cv2.minAreaRect on the content block.5 If the absolute skew angle is greater than a configurable threshold (e.g., 0.5 degrees), the system shall automatically de-skew the image for all subsequent analysis steps. The JSON output shall report the original detected angle.FR-3.3: The system shall calculate a heuristic "noise_score" to identify potential issues like heavy stains, ink bleed-through, or "salt-and-pepper" noise. The JSON output shall report this score.FR-3.4: The system shall report the image resolution (width x height) in pixels.FR-3.5: The system shall attempt to read the image's DPI (dots per inch) from its metadata (e.g., PDF image info or JPG EXIF tags).FR-3.6: If the detected DPI is below a configurable threshold (e.g., 300 DPI) or metadata is unavailable, the system shall upsample the image. The upsampling shall use a high-quality interpolation method suitable for OCR, such as cv2.INTER_CUBIC or cv2.INTER_LANCZOS4. The JSON output shall report the original DPI and whether an upsampling correction was applied.FR-3.7: For "Image-Only" and "Hybrid" PDF pages, the system shall apply an adaptive thresholding method (e.g., cv2.adaptiveThreshold) to create a clean, binarized image for all subsequent layout and content analysis. This is required as global thresholding methods often fail on documents with non-uniform illumination.FR-4: Layout Analysis (Per-page)For all image files and all PDF pages (using the corrected, de-skewed, and binarized image from FR-3):FR-4.1: The system shall use a deep learning object detection model trained on the DocLayNet dataset.6FR-4.2: The system shall detect and provide bounding boxes for all 11 of the following layout classes 6:CaptionFootnoteFormulaList-ItemPage-FooterPage-HeaderPictureSection-HeaderTableTextTitleFR-4.3: The output for each detected layout element shall include its class_label (e.g., "Table") and its page bounding_box coordinates (e.g., [x1, y1, x2, y2]).FR-4.4: The system shall provide a count of column_count (e.g., 1 or 2) by analyzing the spatial relationship of detected Text blocks.FR-5: Specialized Content Detection (Per-page)FR-5.1: Mathematical Content: The system shall identify all mathematical equations on a page by providing the bounding boxes for the Formula class (as per FR-4.2).8FR-5.2: Handwritten Content:FR-5.2.1: The system shall process all regions detected as Text (from FR-4.2).FR-5.2.2: The system shall classify each Text region as either "Printed" or "Handwritten".9 This classification shall be added as a property to the Text layout element in the JSON output.FR-5.3: Language Detection:FR-5.3.1: The system shall perform language detection on the document.FR-5.3.2: The system shall report the primary detected language(s) (e.g., ['en', 'fr']).FR-5.3.3: The system shall explicitly flag the presence of Non-Latin scripts (e.g., Arabic, Chinese, Japanese).123.0 Non-Functional Requirements (NFR)NFR-1: PerformanceNFR-1.1: Throughput (Batch): The system must be capable of processing a batch of 100 mixed-type documents (avg. 5 pages each) in under 15 minutes.NFR-1.2: Latency (Single-File): The end-to-end processing time for a single 10-page document (mixed born-digital and scanned) shall not exceed 60 seconds.NFR-1.3: Latency (Single-Image): The end-to-end processing time for a single .jpg page shall not exceed 5 seconds.NFR-1.4: Resource-CV: The layout analysis model (FR-4.1) must be runnable on a standard CPU but should be optimized for GPU (e.g., NVIDIA T4 or higher).NFR-2: Accuracy & ReliabilityNFR-2.1: File Classification: PDF type classification (FR-2.1) shall be 99.9% accurate on the validation test set.NFR-2.2: Skew Accuracy: Skew angle detection (FR-3.2) shall be accurate to within $+/- 0.5$ degrees.NFR-2.3: Layout Model Accuracy: The layout detection model (FR-4.1) shall achieve a mean Average Precision (mAP) of at least 0.85 on the DocLayNet validation dataset.7NFR-2.4: Content Classification Accuracy: The "Handwritten" vs. "Printed" classifier (FR-5.2) shall achieve an F1-score of at least 0.90 on the validation test set.NFR-2.5: Error Handling: The system shall log all processing errors (per FR-1.4) without crashing or terminating the parent process/service. It must return a valid error-state JSON.NFR-3: Maintainability & ExtensibilityNFR-3.1: Configurability: All detection and correction thresholds (e.g., blur_threshold, skew_threshold, target_dpi) shall be externalized into a configuration file (e.g., .yaml or .env) and not hard-coded.NFR-3.2: Model Swapping: The layout detection model (FR-4.1) shall be loaded from a path specified in the configuration file, allowing the model file to be updated (e.g., a "v2" model) without requiring a new code deployment.NFR-3.3: Code Quality: The system's code shall adhere to team-defined linting standards and include docstrings for all major functions and classes.NFR-4: Deployment & OperationsNFR-4.1: Containerization: The system shall be delivered as a containerized application (e.g., a Dockerfile and pre-built image on the internal registry).NFR-4.2: Logging: The system shall generate structured, human-readable logs (e.g., JSON-formatted) for all major processing steps (e.g., file_received, analysis_started, correction_applied: de-skew, analysis_complete, error_occurred). All logs shall be written to stdout/stderr.NFR-4.3: Statelessness: The application shall be stateless. It must not rely on local disk for anything other than temporary file processing and must not maintain in-memory session data between requests.
