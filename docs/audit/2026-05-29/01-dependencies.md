# Dependencies & Supply Chain Audit (2026-05-29)

Domain summary: uv-managed Python project (requires-python >=3.10,<3.15) with a healthy uv.lock and uv-export requirements files, but the Docker build path still uses Poetry against a non-existent poetry.lock, two divergent copies of the requirements files exist, and the base install still targets Python 3.10 which is near end of upstream security support.

## Findings

### DEP-01: Dockerfiles build with Poetry against a missing poetry.lock (uv project)

- Severity: High
- Effort: M (few days)
- Affected files: `Dockerfile:5-34`, `Dockerfile:65-66`, `Dockerfile.gpu` (same pattern)
- Evidence: Build stage installs Poetry (`ENV POETRY_VERSION=2.1.1`), copies `pyproject.toml poetry.lock* ./` (Dockerfile:26), then `RUN poetry export -f requirements.txt --without-hashes --extras api > requirements.txt` (Dockerfile:34). No `poetry.lock` exists in the repo (`ls poetry.lock` -> No such file). The `poetry.lock*` glob silently matches nothing, so `poetry export` resolves dependencies fresh at build time from PyPI rather than from the committed `uv.lock`. The container build is therefore non-reproducible and bypasses the audited lockfile.
- Recommendation: Switch the Docker build to uv (`uv export` or `uv pip install` against `uv.lock`), or commit a poetry.lock. Reproducible container builds must consume the same pinned lockfile as CI.

### DEP-02: Two divergent copies of the autogenerated requirements files

- Severity: Medium
- Effort: S (<1 day)
- Affected files: `requirements.txt`, `requirements-ml.txt`, `requirements-dev.txt`, `requirements-api.txt` and the duplicate set under `requirements/`
- Evidence: Both the repo-root files and `requirements/*.txt` carry the same `# This file was autogenerated by uv via ... uv export` header (so both are legitimate uv exports, not hand-maintained residue). They have drifted: root `requirements.txt` pins `gitpython==3.1.46` while `requirements/requirements.txt` pins `gitpython==3.1.49`. Drifting line counts per pair: requirements.txt 1, requirements-ml.txt 3, requirements-dev.txt 9, requirements-api.txt 4. Last commit touching `requirements/` is 2026-05-07 (#161, cuda bump); root `requirements.txt` last changed 2026-03-07 (#150), so the root copies are the stale set. No workflow references `requirements/` (mkdocs.yml line 253 references a docs file, not these). The Dockerfile regenerates its own file (see DEP-01), so neither tracked copy is consumed by the container.
- Recommendation: Keep one canonical location, delete the other, and add a CI check (or pre-commit) that fails if `uv export` output differs from the committed file so the copies cannot drift again.

### DEP-03: Base runtime still targets Python 3.10 (near upstream EOL)

- Severity: Medium
- Effort: M (few days)
- Affected files: `pyproject.toml:9` (`requires-python = ">=3.10,<3.15"`), classifiers `pyproject.toml:16-21`, `uv.lock:3` (`requires-python = ">=3.10, <3.15"`)
- Evidence: Floor is Python 3.10. Upstream CPython 3.10 reaches end of security support in October 2026 (roughly 5 months from the 2026-05-29 audit date). Docker images pin `python:3.11-slim` (Dockerfile and Dockerfile.gpu), so containers are not on 3.10, but the declared support floor and lock resolution markers still include 3.10 and 3.10-only wheels.
- Recommendation: Plan to raise the floor to `>=3.11` before 3.10 EOL in October 2026; verify no dependency requires 3.10-specific resolution. Low urgency now, but it crosses into High once inside the 6-month EOL window.

### DEP-04: Unpinned and effectively unmaintained ML dependencies

- Severity: Medium
- Effort: S (<1 day)
- Affected files: `pyproject.toml` `ml`/`colab` extras (`doclayout-yolo`), `labeling`/`language-detection` extras (`fasttext>=0.9.3`)
- Evidence: `doclayout-yolo` is declared with no version specifier at all (bare `"doclayout-yolo"`), resolving to `0.0.4` in uv.lock. A `0.0.x` package with no floor is a supply-chain risk: any future release (including a malicious or breaking one) is accepted. `fasttext` is pinned `>=0.9.3` and resolves to `0.9.3`; Facebook/Meta fastText has had no PyPI release since 0.9.3 (April 2024, over 18 months before this audit) and the upstream repo is in maintenance-only state. Both are confined to optional ML extras, not the base install.
- Recommendation: Add an explicit version floor and upper bound for `doclayout-yolo`. For `fasttext`, document it as a frozen/abandoned dependency and evaluate `fasttext-wheel` or `lingua` (already a dependency in `language-detection`) as a replacement.

### DEP-05: SBOM excludes the iqa extra (pyiqa) by design

- Severity: Low
- Effort: S (<1 day)
- Affected files: `.github/workflows/sbom.yml:55-70`
- Evidence: The SBOM `requirements-complete.txt` enumerates extras explicitly and omits `--extra iqa` because `iqa` and `labeling` declare conflicting `transformers` versions (`==4.37.2` vs `>=4.40.0`, see `pyproject.toml [tool.uv.conflicts]`). The workflow comment states "The only package missed is pyiqa itself." So `pyiqa` and any of its unique transitive deps are absent from the complete SBOM. SBOMs are generated from `uv pip compile` output (not `uv.lock` directly) via cyclonedx-py 4.6.1, and only uploaded as artifacts (no push to a registry / no signing visible in this job).
- Recommendation: Generate a separate SBOM for the `iqa` extra and merge, or note the known gap in the SBOM metadata. Low risk because pyiqa is research-only, but a complete SBOM should not silently drop a declared extra.

## Clean areas

- uv.lock present (2.1 MB), lockfile format version 1 / revision 3, `requires-python` matches pyproject.toml; lockfile is the source of truth for CI.
- requirements*.txt are genuinely `uv export` autogenerated (header verified), not stale hand-maintained residue.
- No prior-tooling migration residue: no setup.py, setup.cfg, poetry.lock, Pipfile, or Pipfile.lock in the repo.
- Transitive-CVE pins are tracked deliberately in base deps (protobuf>=6.33.5, pyasn1>=0.6.2, urllib3>=2.6.3, werkzeug>=3.1.6) with inline justifications.
- Base image tags are pinned (python:3.11-slim, nvidia/cuda:12.1.1-cudnn8-runtime-ubuntu22.04); APT unpinning is documented as intentional for security floats.
- sbom.yml runs on dependency-change PRs, pushes, and a weekly cron; GitHub Actions are SHA-pinned.
